# 스프린트 3 스토리: Kafka 비동기 저장 + 장애 실습

> 상태: **확정** (2026-10-18)

## 결정 사항
- **앱 2개 실행**: 같은 코드를 API용(8080, 컨슈머 끔)과 컨슈머용(8081, 컨슈머 켬)으로 띄운다. 설정 `consumer.enabled`로 리스너를 켜고 끈다. IntelliJ에서 컨슈머 앱만 죽였다 살릴 수 있다.
- **메시지 형식**: key = `couponId`, value = `userId`, 둘 다 문자열. JSON 직렬화 설정 없이 Kafka 개념에 집중.
- **DLQ 실패 유발**: 테스트용으로 `userId == 13`이면 컨슈머가 일부러 예외를 던진다. 실험 후 제거.
- 엔드포인트 규칙 유지: `/issue/kafka` 추가, k6는 `-e MODE=kafka`.

## S3-1. Kafka 연결
- **스토리**: 학습자로서 Spring 앱에서 Kafka로 메시지를 보내고 받고 싶다.
- **수용 기준**
  - `docker compose up -d kafka`로 Kafka 기동.
  - spring-kafka 의존성 추가, `coupon-issued` 토픽에 메시지 1건 발행·수신 확인.
- **의존성**: 없음

## S3-2. 발급 이벤트 발행 (Producer)
- **스토리**: 학습자로서 API가 DB 저장을 기다리지 않고 바로 응답하게 만들고 싶다.
- **수용 기준**
  - `POST /coupons/{id}/issue/kafka?userId=` — `SADD`·`INCR` 검사(S2-3과 동일) → 통과 시 `coupon-issued` 발행 → 즉시 200.
  - 메시지 key = `couponId` (같은 쿠폰은 같은 파티션에 순서대로).
- **의존성**: S3-1, S2-3

## S3-3. 이벤트 저장 (Consumer)
- **스토리**: 학습자로서 컨슈머가 이벤트를 받아 DB에 저장하게 만들고 싶다.
- **수용 기준**
  - `@KafkaListener`가 `coupon-issued`를 받아 `coupon_issue`에 저장. `consumer.enabled=false`면 리스너가 뜨지 않음.
  - k6: 200이 **정확히 100**, 잠시 후 DB 행 수 100.
  - 응답 시간을 `/issue/redis`와 비교.
- **의존성**: S3-2

## S3-4. 컨슈머 장애 실습
- **스토리**: 학습자로서 컨슈머가 죽었다 살아나도 메시지를 잃지 않는다는 것을 확인하고 싶다.
- **수용 기준**
  - 컨슈머 앱을 끈 상태에서 k6 → API는 200 응답, DB는 0건.
  - 컨슈머 앱을 다시 켜면 밀린 메시지를 처리해 DB 100건.
  - `kafka-consumer-groups.sh --describe`로 offset·lag가 줄어드는 것을 확인.
- **의존성**: S3-3

## S3-5. 중복 수신 멱등 처리
- **스토리**: 학습자로서 같은 메시지가 두 번 와도 발급이 한 번만 되게 하고 싶다.
- **수용 기준**
  - 같은 메시지를 수동으로 두 번 발행해도 DB는 1행.
  - unique 제약 위반(`DataIntegrityViolationException`)은 "이미 처리됨"으로 보고 무시 (재시도하지 않음).
- **의존성**: S3-3

## S3-6. 실패 메시지는 DLQ로
- **스토리**: 학습자로서 계속 실패하는 메시지 하나 때문에 컨슈머 전체가 막히지 않게 하고 싶다.
- **수용 기준**
  - `userId == 13`이면 예외 → 몇 번 재시도 후 `coupon-issued.DLT` 토픽으로 이동.
  - 나머지 메시지는 정상 처리 (13번이 당첨자라면 DB 99건 + DLT 1건). 13번 당첨이 불확실하면 curl로 13번 요청을 직접 보내 확인.
  - DLT 토픽에 실패 메시지가 있는 것을 확인.
- **의존성**: S3-3
