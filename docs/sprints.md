# 스프린트 계획: 선착순 쿠폰 발급 시스템

> 상태: **확정** (2026-10-10)

## 결정 사항
- 인프라: Docker Compose로 PostgreSQL·Redis·Kafka를 스프린트 1에서 한 번에 띄운다.
- 검증: JUnit 테스트 없이 k6 부하 테스트로만 검증한다.

| 스프린트 | 목표 | 끝나면 할 수 있는 것 |
|---|---|---|
| 1. 환경 + 버그 재현 | Docker Compose(PG·Redis·Kafka), Spring 프로젝트, API 2개, k6 스크립트 | 초과 발급 버그를 눈으로 본다 |
| 2. Redis로 동시성 해결 | 분산락(Redisson) → `INCR`+`SADD` 순서로 적용, 비교 | 락 방식과 원자 연산 방식의 차이를 안다 |
| 3. Kafka 비동기 + 장애 | 발급 이벤트 발행/컨슈머 저장, 컨슈머 종료 실습, 멱등, DLQ | Kafka가 버퍼 역할을 하고 장애에서 어떻게 복구되는지 안다 |
| 4. Redis 대기열 | Sorted Set 대기열, 스케줄러 발급, 순번 조회 | 선착순 "줄 세우기"를 구현할 수 있다 |

## 왜 이렇게 나눴나
- **1 → 2 순서**: 버그를 먼저 봐야 Redis가 왜 필요한지 남는다. 1번의 k6 스크립트가 이후 모든 스프린트의 검증 도구가 된다.
- **2에서 락 → 원자 연산**: 락이 더 직관적이라 먼저, 그다음 "락 없이도 된다"를 보여주는 흐름. 같은 k6로 바로 비교.
- **3은 2 위에 쌓는다**: Kafka는 Redis 검증을 통과한 요청만 받는 구조라 2가 끝나야 한다. 장애 실습은 같은 코드에서 바로 하므로 한 스프린트로 묶음.
- **4를 마지막에**: 대기열은 발급 앞단에 붙는 독립 기능이라 다른 스프린트에 의존하지 않는다. 기간이 부족하면 여기서 잘라도 1~3의 학습은 온전하다.
- 인프라(Docker Compose)는 스프린트 1에서 세 개를 한 번에 띄운다. 나중에 붙이는 것보다 파일 하나 고치는 수고가 적다.

## 스프린트 1: 환경 + 버그 재현
- `docker-compose.yml`: PostgreSQL, Redis, Kafka(KRaft, Zookeeper 없음)
- 기존 프로젝트(Boot 4.1.1)에 JPA, PostgreSQL 의존성 추가
- `coupon`, `coupon_issue` 엔티티 + API 2개 (조회 → 차감 → 저장, 아무 보호 없이)
- k6 스크립트: 동시 1000건, 끝나고 발급 건수 확인

## 스프린트 2: Redis로 동시성 해결
- Redisson 분산락으로 발급 로직 감싸기 → k6로 100건 확인
- `INCR` + `SADD` 방식으로 교체 → k6로 100건 확인, 소요 시간 체감 비교

## 스프린트 3: Kafka 비동기 + 장애
- API: Redis 검증 통과 시 `coupon-issued` 이벤트 발행 후 즉시 응답
- 컨슈머: 이벤트 받아 DB 저장
- 실습: 컨슈머 종료 → 요청 → 재시작 → 밀린 메시지 처리 확인
- 중복 수신 시 unique 제약으로 멱등 처리, 실패 메시지 DLQ 전송

## 스프린트 4: Redis 대기열
- 발급 요청 → `ZADD`로 대기열 등록, `ZRANK`로 순번 조회 API
- 스케줄러가 1초마다 앞에서 N명 꺼내 발급 (스프린트 2·3 로직 재사용)

## 회고

### 스프린트 1 (완료 2026-10-16)
- 결과: 수량 100 쿠폰에 동시 1000건 → **766건 발급** (`issued_quantity`는 100). Lost Update 재현 성공.
- 변경: PostgreSQL은 Docker 대신 로컬 설치본 사용. DB 비밀번호는 `.env`(gitignore)로 분리.
- 배운 점: Windows PowerShell 5.1에서 `Get-Content | docker run`은 한글이 깨짐 → k6는 볼륨 마운트로 실행.

### 스프린트 2 (완료)
- 결과: `/issue/lock`(Redisson 분산락), `/issue/redis`(`SADD`+`INCR`) 둘 다 동시 1000건에 발급 정확히 100건.
- 변경: `spring-boot-starter-data-redis`는 따로 추가하지 않음. Redisson 스타터에 이미 포함되어 있어 `StringRedisTemplate`을 바로 사용.
- 배운 점: 락은 트랜잭션 **바깥**에서 잡아야 함 (락 → 트랜잭션 시작 → 커밋 → 락 해제). 원자 연산 방식은 락 대기가 없어 더 빠르고, 기준이 DB가 아니라 Redis 카운터가 됨.

### 스프린트 3 (완료 2026-10-26)
- 결과
  - S3-5: 같은 메시지(`1:998`)를 console producer로 두 번 발행 → insert 2회 중 두 번째가 unique 위반, `중복 무시` 한 번 출력, 재시도 없음. DB 1행.
  - S3-6: `1:13` 발행 → 1초 간격 재시도 2회(`Seeking to offset ...` 로그) 후 DLT로 이동, 뒤에 보낸 `1:9001`/`1:9002`는 정상 저장.
- 변경
  - 컨슈머 앱도 Redisson 빈을 만들기 때문에 8081만 띄울 때도 Redis가 켜져 있어야 함.
  - DLT 토픽 이름을 `coupon-issued.DLT` → `coupon-issued-dlt`로 변경 (Spring Kafka 4.x 기본값).
  - S3-6 검증은 k6 대신 console producer로 13번 메시지를 직접 보내서 함.
- 배운 점
  - Kafka는 "최소 한 번" 전달 → 컨슈머는 멱등이어야 함. 판정은 DB unique 제약에 맡기고, 위반은 catch로 삼켜야 재시도로 안 넘어감.
  - 예외 종류를 나눠야 함: "다시 해도 소용없는 정상 상황"(중복)은 삼키고, 진짜 실패는 재시도 후 DLT.
  - 같은 key는 같은 파티션 → 순서대로 처리되므로, 실패 메시지가 재시도하는 동안 뒤 메시지가 기다림. 무한 재시도면 파티션이 막힘.
  - DLT 이름을 틀리면 Kafka가 토픽을 **파티션 1개로 자동 생성**해서 조용히 그쪽으로 감. 원래 파티션 번호로 보내기 때문에 파티션 수가 다르면 전송 실패할 수 있음. `kafka-topics.sh --list`로 확인할 것.
- 마무리: DLT 토픽 이름 변경 후 파티션 3개로 늘어난 것 확인, `userId == 13` 실패 코드 제거.
